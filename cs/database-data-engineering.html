数据库与数据工程

从关系模型到时序数据库，覆盖 SQL、索引、事务、 数据仓库与数据管道。数据库与数据工程是地震目录管理、 波形归档与大规模数据处理的基础设施， 也是"数据驱动"研究的前提。

SQL 索引 时序数据库 数据管道

§引言

数据库研究数据的持久化存储、高效检索与一致性维护； 数据工程研究数据从产生到使用的完整流程—— 采集、清洗、存储、加工、分发、消费。

在地震学与地震工程中，数据量正在快速增长：

  • 全球地震台网每天产生的连续波形达数 TB。
  • 地震目录（USGS、ISC、中国地震台网）已积累数百万条事件记录。
  • 强震记录库（PEER NGA、ESM、K-NET）有数十万条记录。
  • 地震预警系统需要毫秒级的数据流处理。
  • 机器学习训练数据集（STEAD、INSTANCE）达 100 GB 级。

这些数据的管理需要专门的技术：

数据类型典型规模存储方案
地震事件目录 10⁵~10⁷ 条 关系数据库（PostgreSQL）
台站元数据 10³~10⁵ 个 关系数据库
连续波形 10¹²~10¹⁵ 采样点 时序数据库 / 文件存储
强震记录 10⁵~10⁶ 条 文件 + 元数据数据库
机器学习数据集 10¹¹~10¹² 字节 对象存储 + 数据湖
实时数据流 MB/s ~ GB/s 消息队列 + 时序数据库

这份笔记按"模型 $\to$ SQL $\to$ 索引 $\to$ 事务 $\to$ 时序 $\to$ 仓库 $\to$ 管道 $\to$ 应用" 的顺序梳理，每一节都尽量落到工程语境上。

01数据模型

数据库的分类

类型数据模型代表适用场景
关系型（RDBMS） 表 + 行 + 列 PostgreSQL、MySQL、SQLite 结构化数据、强一致性
文档型 JSON 文档 MongoDB、CouchDB 半结构化数据
键值型 key-value Redis、DynamoDB 缓存、快速查找
列式存储 列族 Cassandra、HBase 大规模写入、分析
时序数据库（TSDB） 时间索引的测量值 InfluxDB、TimescaleDB 传感器、监控、波形
图数据库 节点 + 边 Neo4j、JanusGraph 关系网络分析
空间数据库 几何对象 + 空间索引 PostGIS 地震、GIS

关系模型

关系模型的核心概念：

  • 表（Relation）：二维结构，行是记录，列是属性。
  • 主键（Primary Key）：唯一标识一行。
  • 外键（Foreign Key）：引用另一张表的主键。
  • 约束（Constraint）：NOT NULL、UNIQUE、CHECK。
  • 范式（Normal Form）：减少冗余、避免更新异常。

地震目录数据库设计示例

-- 事件表
CREATE TABLE events (
    event_id    VARCHAR(20) PRIMARY KEY,
    origin_time TIMESTAMPTZ NOT NULL,
    latitude    DOUBLE PRECISION NOT NULL,
    longitude   DOUBLE PRECISION NOT NULL,
    depth_km    DOUBLE PRECISION,
    magnitude   DOUBLE PRECISION,
    mag_type    VARCHAR(10),
    region      VARCHAR(100),
    catalog     VARCHAR(20)
);

-- 台站表
CREATE TABLE stations (
    station_id  VARCHAR(20) PRIMARY KEY,
    network     VARCHAR(10),
    latitude    DOUBLE PRECISION NOT NULL,
    longitude   DOUBLE PRECISION NOT NULL,
    elevation_m DOUBLE PRECISION,
    vs30        DOUBLE PRECISION,
    site_class  VARCHAR(5),
    start_date  DATE,
    end_date    DATE
);

-- 波形记录表（元数据，波形本身存在文件或对象存储）
CREATE TABLE waveforms (
    waveform_id BIGSERIAL PRIMARY KEY,
    event_id    VARCHAR(20) REFERENCES events(event_id),
    station_id  VARCHAR(20) REFERENCES stations(station_id),
    channel     VARCHAR(10),
    start_time  TIMESTAMPTZ NOT NULL,
    sample_rate DOUBLE PRECISION,
    npts        INTEGER,
    file_path   TEXT,
    quality     VARCHAR(5)
);

-- 索引
CREATE INDEX idx_events_time ON events(origin_time);
CREATE INDEX idx_events_mag  ON events(magnitude);
CREATE INDEX idx_events_loc  ON events(latitude, longitude);
CREATE INDEX idx_waveforms_event ON waveforms(event_id);

范式与反范式

范式要求解决的问题
1NF 每列不可再分 消除重复组
2NF 非主属性完全依赖主键 消除部分依赖
3NF 非主属性不传递依赖主键 消除传递依赖
BCNF 每个决定因子都是候选键 更强的 3NF

工程中，范式化与反范式化需要权衡：

  • 范式化：减少冗余、保证一致性；但查询需要大量 JOIN。
  • 反范式化：冗余存储、查询更快；但更新复杂、易不一致。
  • 常见折中：OLTP 用范式化，OLAP 用星型/雪花模型。
💡

地震数据的特点： ① 时空属性强——时间、经纬度是核心维度， 需要时空索引； ② 多层次结构——事件、台站、波形、参数等多表关联； ③ 数据量大——波形数据不适合放在关系表， 用文件系统或对象存储； ④ 元数据与数据分离——元数据放数据库， 原始数据放文件或对象存储，用路径关联。 这是地震数据中心的标准架构。

02SQL 与查询

基础查询

-- 查询所有震级大于 5.0 的事件
SELECT event_id, origin_time, magnitude, latitude, longitude
FROM events
WHERE magnitude > 5.0
ORDER BY origin_time DESC
LIMIT 100;

-- 聚合
SELECT
    DATE_TRUNC('month', origin_time) AS month,
    COUNT(*) AS n_events,
    AVG(magnitude) AS avg_mag,
    MAX(magnitude) AS max_mag
FROM events
WHERE origin_time >= '2000-01-01'
GROUP BY month
ORDER BY month;

-- 分组 + HAVING
SELECT region, COUNT(*) AS n
FROM events
GROUP BY region
HAVING COUNT(*) > 100
ORDER BY n DESC;

JOIN

-- INNER JOIN：只保留两表都匹配的行
SELECT e.event_id, e.magnitude, w.station_id, w.quality
FROM events e
INNER JOIN waveforms w ON e.event_id = w.event_id
WHERE e.magnitude > 5.0;

-- LEFT JOIN：保留左表所有行
SELECT e.event_id, e.magnitude, COUNT(w.waveform_id) AS n_records
FROM events e
LEFT JOIN waveforms w ON e.event_id = w.event_id
GROUP BY e.event_id, e.magnitude;

-- 多表 JOIN
SELECT e.event_id, e.magnitude, s.station_id, s.vs30
FROM events e
JOIN waveforms w ON e.event_id = w.event_id
JOIN stations s ON w.station_id = s.station_id
WHERE e.magnitude > 6.0;

子查询与 CTE

-- 子查询
SELECT * FROM events
WHERE magnitude > (
    SELECT AVG(magnitude) FROM events
);

-- CTE（WITH）：更易读的复杂查询
WITH mag_stats AS (
    SELECT DATE_TRUNC('year', origin_time) AS year,
           AVG(magnitude) AS avg_mag
    FROM events
    GROUP BY year
)
SELECT * FROM mag_stats
WHERE avg_mag > 5.0
ORDER BY year;

-- 窗口函数
SELECT
    event_id,
    origin_time,
    magnitude,
    ROW_NUMBER() OVER (ORDER BY magnitude DESC) AS rank,
    AVG(magnitude) OVER (
        ORDER BY origin_time
        ROWS BETWEEN 99 PRECEDING AND CURRENT ROW
    ) AS rolling_avg
FROM events;

空间查询（PostGIS）

-- 启用 PostGIS 扩展
CREATE EXTENSION postgis;

-- 添加几何列
ALTER TABLE events ADD COLUMN geom GEOMETRY(POINT, 4326);
UPDATE events SET geom = ST_SetSRID(
    ST_MakePoint(longitude, latitude), 4326
);

-- 空间索引
CREATE INDEX idx_events_geom ON events USING GIST(geom);

-- 查询某个矩形范围内的地震
SELECT event_id, magnitude
FROM events
WHERE geom && ST_MakeEnvelope(100, 30, 102, 32, 4326);

-- 查询距离某点 100 km 内的地震
SELECT event_id, magnitude,
       ST_Distance(geom::geography,
                   ST_MakePoint(101, 31)::geography) / 1000 AS dist_km
FROM events
WHERE ST_DWithin(
    geom::geography,
    ST_MakePoint(101, 31)::geography,
    100000
)
ORDER BY dist_km
LIMIT 50;

            WHERE magnitude >= :min_mag
            ORDER BY origin_time DESC
            LIMIT :limit

03索引与优化

索引原理

索引是加速查询的数据结构。最常见的是 B+ 树： 所有数据在叶节点，内部节点只存键值用于导航。

为什么 B+ 树适合数据库：

  • 高度低（通常 3~4 层），节点大小与磁盘块对齐。
  • 叶节点有序连接，支持范围查询。
  • 插入删除代价低，自动平衡。

索引类型

类型结构适用典型场景
B 树 平衡树 等值、范围 主键、外键、时间
哈希 哈希表 等值 精确查找
GIST 通用搜索树 几何、多维 PostGIS 空间查询
GIN 倒排索引 数组、全文、JSON 标签、文本搜索
BRIN 块范围索引 有序大表 时序数据
复合索引 多列 B 树 多条件查询 时间 + 震级

索引设计原则

  • 为 WHERE、JOIN、ORDER BY 建索引：这些是查询的热点。
  • 复合索引的最左前缀原则：(a, b) 可加速 a、(a, b)，但不加速单独 b。
  • 选择性高的列优先：区分度大的列更适合放前面。
  • 避免过度索引：每个索引占用存储、拖慢写入。
  • 覆盖索引：索引包含查询所需全部列，避免回表。
  • 部分索引：只对满足条件的行建索引（如 WHERE magnitude > 4）。
-- 复合索引：时间 + 震级
CREATE INDEX idx_events_time_mag ON events(origin_time, magnitude);

-- 部分索引：只对大地震建索引
CREATE INDEX idx_large_events
ON events(origin_time)
WHERE magnitude > 6.0;

-- 表达式索引：按月份查询
CREATE INDEX idx_events_month
ON events(DATE_TRUNC('month', origin_time));

-- 覆盖索引
CREATE INDEX idx_events_covering
ON events(magnitude) INCLUDE (event_id, origin_time);

-- 查看执行计划
EXPLAIN ANALYZE
SELECT * FROM events WHERE magnitude > 6.0;

查询优化技巧

问题原因优化
全表扫描 无索引或条件无法用索引 建索引、重写条件
索引失效 列上有函数或类型转换 改为函数索引或改写
大量 JOIN 范式化过度 适当反范式、物化视图
SELECT * 读取不需要的列 只选必要列
OFFSET 分页 扫描前面所有行 用 keyset 分页
ORDER BY 慢 无排序索引 建对应复合索引
子查询重复计算 优化器不缓存 用 CTE 或临时表

分区表

对大表按某列分区，可以显著提升查询和维护效率： 

-- 按年份分区（PostgreSQL 声明式分区）
CREATE TABLE events (
    event_id    VARCHAR(20),
    origin_time TIMESTAMPTZ NOT NULL,
    magnitude   DOUBLE PRECISION,
    ...
) PARTITION BY RANGE (origin_time);

CREATE TABLE events_2023 PARTITION OF events
FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE events_2024 PARTITION OF events
FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

-- 查询时优化器自动裁剪分区
SELECT * FROM events
WHERE origin_time >= '2024-01-01'
  AND origin_time <  '2024-07-01';
-- 只扫描 events_2024 分区
💡

时空索引的挑战： 地震数据查询通常是时空混合： "查询某个矩形范围内、某时间段内的地震"。 单列索引（时间或空间）只能加速一半条件。 常见方案： ① 复合索引 (origin_time, geom) 或 (geom, origin_time)，根据查询模式选择； ② 时空索引：PostGIS 支持 ST_Index， 或使用时序数据库的空间扩展； ③ 分区 + 空间索引：先按时间分区， 再在每个分区内建空间索引。

04事务与并发

ACID 特性

事务是一组要么全部成功、要么全部失败的操作。 它满足四个特性：

特性含义保证
原子性（Atomicity） 事务内的操作要么全做，要么全不做 日志 + 回滚
一致性（Consistency） 事务前后数据满足约束 约束检查
隔离性（Isolation） 并发事务互不干扰 锁 / MVCC
持久性（Durability） 提交后数据永久保存 WAL 日志 + fsync

事务示例

BEGIN;

-- 插入事件
INSERT INTO events (event_id, origin_time, magnitude, latitude, longitude)
VALUES ('ev2024001', '2024-06-01 12:00:00+00', 6.5, 30.5, 101.2);

-- 插入关联的波形记录
INSERT INTO waveforms (event_id, station_id, channel, start_time, npts)
VALUES
    ('ev2024001', 'ST01', 'BHZ', '2024-06-01 12:00:05+00', 6000),
    ('ev2024001', 'ST02', 'BHZ', '2024-06-01 12:00:08+00', 6000);

-- 若任一步失败，全部回滚
COMMIT;
-- 或 ROLLBACK;

隔离级别

SQL 标准定义四个隔离级别，级别越高越安全但并发度越低：

级别脏读不可重复读幻读典型应用
READ UNCOMMITTED 可能 可能 可能 几乎不用
READ COMMITTED 否 可能 可能 PostgreSQL 默认
REPEATABLE READ 否 否 可能 MySQL InnoDB 默认
SERIALIZABLE 否 否 否 金融、强一致场景

MVCC：多版本并发控制

现代数据库（PostgreSQL、Oracle、MySQL InnoDB）用 MVCC 替代锁：

  • 每行数据保留多个版本。
  • 读操作读取快照版本，不阻塞写。
  • 写操作创建新版本，不阻塞读。
  • 旧版本在无事务引用后清理（vacuum）。

MVCC 的代价：存储开销（多版本）与清理开销（vacuum）。 PostgreSQL 需要定期 VACUUM 或自动清理。

分布式事务

当数据分布在多个节点时，需要分布式事务：

  • 两阶段提交（2PC）：prepare + commit，经典但阻塞。
  • 三阶段提交（3PC）：加预提交，减少阻塞。
  • Paxos / Raft：共识协议，用于分布式数据库。
  • Saga 模式：长事务拆分为多个本地事务 + 补偿。

工程实践中的常见选择：

  • 强一致：单机 PostgreSQL、MySQL。
  • 分布式强一致：CockroachDB、TiDB、Spanner。
  • 最终一致：Cassandra、DynamoDB + 应用层补偿。

05时序数据库

时序数据的特点

时序数据（time series）是按时间顺序排列的测量值：

  • 写多读少：传感器持续产生数据，写入量远大于读取。
  • 时间有序：数据按时间递增，最新数据最重要。
  • 单调增长：数据量随时间线性增长。
  • 时间范围查询：典型查询是某个时间段内的数据。
  • 聚合统计：均值、最大、最小、百分位等。

地震波形正是典型的时序数据： 连续采样的时间序列，采样率 100~500 Hz， 每台站每天产生数百万个采样点。

时序数据库对比

数据库特点适用场景
InfluxDB 专用 TSDB，类 SQL 查询 监控、传感器
TimescaleDB PostgreSQL 扩展 与关系数据混合
Prometheus 监控专用 系统指标
OpenTSDB 基于 HBase 大规模指标
QuestDB 高性能列式 金融、IoT
Cassandra 分布式宽列 超大规模

TimescaleDB 示例

TimescaleDB 是 PostgreSQL 的扩展， 保留了 SQL 的灵活性，同时优化时序性能： 

-- 启用扩展
CREATE EXTENSION IF NOT EXISTS timescaledb;

-- 创建普通表
CREATE TABLE waveform_samples (
    time        TIMESTAMPTZ NOT NULL,
    station_id  VARCHAR(20) NOT NULL,
    channel     VARCHAR(10) NOT NULL,
    value       REAL
);

-- 转换为 hypertable（自动分区）
SELECT create_hypertable('waveform_samples', 'time');

-- 插入数据
INSERT INTO waveform_samples VALUES
    ('2024-06-01 12:00:00+00', 'ST01', 'BHZ', 0.012),
    ('2024-06-01 12:00:00.01+00', 'ST01', 'BHZ', -0.005),
    ...;

-- 时间范围聚合
SELECT
    time_bucket('1 second', time) AS bucket,
    station_id,
    AVG(value) AS avg_val,
    MAX(ABS(value)) AS max_abs
FROM waveform_samples
WHERE time >= '2024-06-01 12:00:00+00'
  AND time <  '2024-06-01 12:01:00+00'
GROUP BY bucket, station_id
ORDER BY bucket;

-- 连续聚合（物化视图）
CREATE MATERIALIZED VIEW waveform_hourly
WITH (timescaledb.continuous) AS
SELECT
    time_bucket('1 hour', time) AS hour,
    station_id,
    AVG(value) AS avg_val
FROM waveform_samples
GROUP BY hour, station_id;

地震波形存储方案

实际地震数据中心通常采用混合存储：

数据类型存储方案理由
原始波形 MiniSEED 文件 + 对象存储 数据量大，格式标准
波形索引 关系数据库 元数据查询
实时流 消息队列 + 时序库 低延迟、高吞吐
处理后波形 时序数据库 快速范围查询
地震目录 关系数据库 + 空间索引 时空查询
机器学习数据集 Parquet / HDF5 高效读取、压缩
💡

为什么不用纯关系数据库存波形： ① 关系数据库的行存储对时序范围查询效率低； ② 每行有开销，存储效率不如二进制文件； ③ 关系数据库的写吞吐量不如专用 TSDB。 但关系数据库在元数据（事件、台站、波形索引）上无可替代。 所以地震数据中心的标准架构是 关系库（元数据）+ 文件/对象存储（波形）+ 时序库（处理后的指标）。

数据仓库模型

星型模型（Star Schema）

中心是事实表（事件、测量）， 周围是维度表（时间、台站、位置）： 

       DimTime
          │
DimStation ─ Fact ─ DimLocation
          │
       DimMagnitude

优点：JOIN 简单，查询快。 缺点：维度表可能冗余。

雪花模型（Snowflake Schema）

维度表进一步范式化，形成多层结构： 

DimTime ─ DimYear ─ DimDecade
   │
Fact ─ DimStation ─ DimNetwork ─ DimCountry
   │
DimLocation ─ DimRegion

优点：减少冗余。 缺点：JOIN 复杂，查询慢。

列式存储

列式存储按列存储数据，对分析查询极高效：

  • 只读所需列：跳过无关列，减少 I/O。
  • 压缩比高：同列类型相同，压缩率高。
  • 向量化计算：批量处理，利用 SIMD。

代表系统：ClickHouse、DuckDB、Parquet（文件格式）。

ClickHouse 示例

-- 创建表
CREATE TABLE events (
    event_id    String,
    origin_time DateTime,
    magnitude   Float64,
    latitude    Float64,
    longitude   Float64,
    depth_km    Float64
) ENGINE = MergeTree()
ORDER BY (origin_time, magnitude);

-- 批量插入
INSERT INTO events VALUES
    ('ev001', '2024-01-01 12:00:00', 6.5, 30.5, 101.2, 15.0),
    ...;

-- 聚合查询（极快）
SELECT
    toYear(origin_time) AS year,
    count(*) AS n,
    avg(magnitude) AS avg_mag,
    quantile(0.95)(magnitude) AS p95
FROM events
WHERE origin_time >= '2000-01-01'
GROUP BY year
ORDER BY year;

数据湖与湖仓一体

数据湖（Data Lake）用对象存储（S3、OSS）存海量原始数据， 配合 Parquet、ORC 等列式格式：

  • 存算分离：存储便宜，计算弹性的云服务。
  • schema-on-read：读取时解释 schema，写入灵活。
  • 支持多引擎：Spark、Presto、DuckDB 都能读。

湖仓一体（Lakehouse）在数据湖之上加了表格式（Delta Lake、Iceberg）， 提供事务、版本、schema 演进能力。 这是当前大数据架构的主流方向。

07数据管道与工程实践

数据管道

数据管道是数据从源到消费的自动化流程： 

数据源 → 采集 → 清洗 → 转换 → 存储 → 服务 → 消费

在地震学中：

  • 采集：从台站实时接收数据流。
  • 清洗：去噪、去尖峰、质量检查。
  • 转换：格式转换、重采样、去趋势。
  • 存储：写入 MiniSEED 文件 + 元数据数据库。
  • 服务：提供 API 供数据查询。
  • 消费：用户下载、机器学习训练。

批处理 vs 流处理

维度批处理流处理
延迟 分钟~小时 毫秒~秒
数据范围 有界（一批） 无界（持续）
典型工具 Spark、DuckDB Kafka Streams、Flink
地震应用 目录更新、建模 预警、实时质控

ETL vs ELT

  • ETL：Extract-Transform-Load，先转换后加载。 适合传统数仓，转换在中间层。
  • ELT：Extract-Load-Transform，先加载后转换。 适合数据湖，利用目标系统的计算能力。

消息队列

消息队列在数据管道中解耦生产者和消费者：

系统特点适用
Kafka 高吞吐、持久化、分布式 大规模数据流
RabbitMQ AMQP、灵活路由 任务队列
Redis Streams 内存、快速 轻量级流处理
NATS 极轻量、低延迟 微服务通信
Pulsar 多租户、分区 大规模消息

地震数据管道的典型架构

台站 → SeedLink → 消息队列（Kafka）
                      │
                      ├→ 实时检测（触发、拾取）
                      │    │
                      │    └→ 预警系统
                      │

数据质量与治理

数据工程不仅是技术，还是流程与规范：

  • 数据契约：上下游约定 schema 与语义。
  • 数据校验：范围、类型、缺失值、一致性。
  • 元数据管理：数据血缘、版本、来源。
  • 数据目录：可搜索的数据资产清单。
  • 访问控制：权限、审计、脱敏。
  • 可观测性：监控数据质量、管道延迟。

Python ETL 示例

etl_pipeline.py Python 
"""
一个简单的地震目录 ETL 管道：
  Extract: 从 CSV 读原始目录
  Transform: 清洗、规范化、计算派生字段
  Load: 写入 SQLite（可替换为 PostgreSQL）
"""
import sqlite3
import logging
from pathlib import Path

import pandas as pd
import numpy as np

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)


def extract(csv_path: Path) -> pd.DataFrame:
    """从 CSV 读取原始目录"""
    logger.info(f"读取 {csv_path}")
    df = pd.read_csv(csv_path)
    logger.info(f"  加载 {len(df)} 行")
    return df


def transform(df: pd.DataFrame) -> pd.DataFrame:
    """清洗与派生字段"""
    logger.info("转换数据")

    # 1. 缺失值处理
    n_before = len(df)
    df = df.dropna(subset=["magnitude", "latitude", "longitude"])
    logger.info(f"  删除缺失关键字段: {n_before - len(df)} 行")

    # 2. 类型转换
    df["origin_time"] = pd.to_datetime(df["origin_time"])
    df["magnitude"] = df["magnitude"].astype(float)

    # 3. 范围校验
    mask = (
        df["magnitude"].between(-2, 10) &
        df["latitude"].between(-90, 90) &
        df["longitude"].between(-180, 180)
    )
    df = df[mask]
    logger.info(f"  范围校验后: {len(df)} 行")

    # 4. 派生字段
    # 地震能量（Gutenberg-Richter）：log10(E) = 1.5M + 4.8
    df["log10_energy"] = 1.5 * df["magnitude"] + 4.8

    # 5. 归一化字段名
    df.columns = [c.lower().strip() for c in df.columns]

    return df


def load(df: pd.DataFrame, db_path: Path, table: str = "events"):
    """写入 SQLite 数据库"""
    logger.info(f"写入 {db_path}")

    with sqlite3.connect(db_path) as conn:
        df.to_sql(table, conn, if_exists="replace", index=False)

    logger.info(f"  写入 {len(df)} 行到表 {table}")


def run_pipeline(csv_path: Path, db_path: Path):
    """运行完整 ETL"""
    df_raw = extract(csv_path)
    df_clean = transform(df_raw)
    load(df_clean, db_path)


if __name__ == "__main__":
    # 生成模拟数据
    rng = np.random.default_rng(42)
    n = 1000
    df = pd.DataFrame({
        "event_id": [f"ev{i:05d}" for i in range(n)],
        "origin_time": pd.date_range("2020-01-01", periods=n, freq="6h"),
        "magnitude": rng.uniform(2.0, 7.5, n),
        "latitude": rng.uniform(28, 34, n),
        "longitude": rng.uniform(98, 104, n),
        "depth_km": rng.exponential(10, n),
    })

    # 故意加入缺失值与异常值
    df.loc[10:15, "magnitude"] = np.nan
    df.loc[20, "latitude"] = 200   # 非法值

    csv_path = Path("catalog_raw.csv")
    df.to_csv(csv_path, index=False)

    db_path = Path("catalog.db")
    run_pipeline(csv_path, db_path)

    # 验证
    with sqlite3.connect(db_path) as conn:
        result = pd.read_sql("SELECT COUNT(*) AS n FROM events", conn)
        print(f"\n数据库中事件数: {result['n'][0]}")

典型查询模式

-- 查询某区域某时间段的强震记录
SELECT e.event_id, e.magnitude, e.origin_time,
       s.station_id, s.vs30, w.file_path
FROM events e
JOIN waveforms w ON e.event_id = w.event_id
JOIN stations s ON w.station_id = s.station_id
WHERE e.origin_time BETWEEN '2020-01-01' AND '2024-12-31'
  AND e.magnitude >= 5.0
  AND ST_DWithin(
        e.geom::geography,
        ST_MakePoint(101, 31)::geography,
        200000  -- 200 km
      )
  AND s.vs30 BETWEEN 200 AND 800;

-- 按站点统计记录数
SELECT s.station_id, COUNT(*) AS n_records,
       AVG(e.magnitude) AS avg_mag,
       MAX(e.magnitude) AS max_mag
FROM events e
JOIN waveforms w ON e.event_id = w.event_id
JOIN stations s ON w.station_id = s.station_id
GROUP BY s.station_id
HAVING COUNT(*) > 100
ORDER BY n_records DESC;

-- 时间序列分析：每月事件数
SELECT
    DATE_TRUNC('month', origin_time) AS month,
    COUNT(*) AS n_events,
    AVG(magnitude) AS avg_mag,
    SUM(CASE WHEN magnitude >= 5 THEN 1 ELSE 0 END) AS n_m5
FROM events
WHERE origin_time >= '2000-01-01'
GROUP BY month
ORDER BY month;

09小结

📌 核心要点

  • 数据模型：关系模型是基础；地震数据用"元数据 + 波形"分离架构。
  • SQL：JOIN、聚合、窗口函数、CTE；PostGIS 提供空间查询。
  • 索引：B+ 树、GIST、GIN、BRIN；时空混合查询需要复合或分区索引。
  • 事务：ACID；隔离级别；MVCC 是现代数据库的核心机制。
  • 时序数据库：适合传感器、波形；TimescaleDB 保留 SQL 能力。
  • 数据仓库：列式存储（ClickHouse、DuckDB）；星型模型适合分析。
  • 数据管道：批处理 + 流处理；消息队列解耦；数据质量与治理至关重要。
  • 地震学应用：数据中心架构、FDSN Web Services、数据格式标准。
